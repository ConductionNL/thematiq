## Context

See proposal.md for why. The editor today:

- is vanilla JavaScript in `js/admin.js`; `initTokenEditor()` and `renderTokenEditor()` build every row of every tab up front from the registry the page receives as initial state;
- keeps unsaved edits in `tokenEditorState`, which is why the panels are not rebuilt on tab switch;
- saves through `CustomOverridesService`, which writes light values on `:root` and, for brand colours, a derived dark value into the two dark scopes (#705).

After changes 2 and 3 the registry holds about 790 tokens, each with a tab or an owning component, an `advanced` flag where it applies, and an inventory entry with Nextcloud's stock value per theme and an optional note.

## Goals / Non-Goals

**Goals:**
- Any token can be found in two keystrokes or one heading.
- The settings page loads no slower than today.
- Each row tells the admin what they are replacing.

**Non-Goals:**
- Redesigning the four theme tabs. They keep their content, plus the new theme tokens.
- Moving the editor to Vue. The panel stays vanilla JavaScript; that is a separate decision.
- Keyboard handling of the tab strip itself. The open `admin-panel-keyboard-accessibility` change owns it; this change only adds controls that are keyboard-operable from the start.

## Decisions

### Render on open, keep state in one place

Each component group and the Advanced group is a disclosure button with `aria-expanded` and an empty panel. Rows are built the first time the panel opens, or when a search matches the group. `tokenEditorState` stays the one store of unsaved values, so a group that is closed and opened again shows the edit, not the saved value.

Alternative considered: virtual scrolling over one list of 790 rows. Rejected. It needs a fixed row height, which the note and the dark field break, and screen readers handle virtualised lists poorly.

### Search filters what exists, and builds what it needs

The search index is a flat array built once from the registry: label, CSS name, the translated group heading and the owner id. Typing filters it; a group with a match is expanded and its rows built; groups without a match are hidden. An empty field restores the previous open state.

### Stock values come from the inventory, resolved in the page

The registry payload carries each token's inventory stock value for the four built-in themes. The row shows the one for the admin's current theme. A stock value that is an expression, such as `var(--color-border)`, is resolved by applying it to a hidden probe element and reading the computed value, so the admin sees a colour, not a formula.

### Dark values are stored as tokens in the dark scopes

The dark field writes the same `--nldesign-*` token inside the two dark scopes `CustomOverridesService` already writes. It outranks the zero-specificity dark reset from change 2. An empty dark field writes nothing, so the reset leaves Nextcloud's dark value in place. Brand rows have no dark field and keep the derived dark value.

### The count is read, never written

The panel heading states `TokenRegistry::getTokens()`'s count, passed in initial state. The two docs pages that say 53 state the same number, generated by the docs build from the registry, so the editor and the docs cannot drift apart again.

### Accessibility

- The search field has a visible label and an accessible name.
- Disclosure buttons expose `aria-expanded` and control their panel by `aria-controls`.
- The Advanced warning is text above the first field, with an icon as decoration only.
- The stock value and the note are associated with their field through `aria-describedby`.

## Risks / Trade-offs

- [The registry payload grows from 179 to about 790 entries] → Measure the initial-state size before and after. If it passes 100 KB, send the internal groups on first open instead.
- [Overlap with `admin-panel-keyboard-accessibility` and the playground fixes another agent is landing (#623 to #627)] → Merge `development` into this branch before each push, and keep the edits to the token editor functions, not the playground.
- [An admin sets a hardcoded colour that breaks a component's own contrast] → The stock value beside the field makes the change visible. Auditing every component pair is out of scope, as in change 3.

## Migration Plan

No stored-data change. An overrides file written before this change holds only brand tokens and imports unchanged. Rollback is reverting the PR; stored internal and dark values stay in the file and are ignored by the older editor.

Not applicable. This change adds no OpenRegister schema.
