# AGENTS.md

Thematiq is a Nextcloud app that applies a house style (NL Design System token sets, La Suite numerique and custom sets) to every Nextcloud screen, edited live from one admin settings page. It is a PHP backend with a vanilla JavaScript admin panel; the app id is `thematiq` (see `appinfo/info.xml`).

## Setup

The repository ships two Docker Compose files. Neither bind-mounts your working copy.

- `docker-compose.yml`: evaluation stack (Nextcloud with thematiq and OpenRegister, PostgreSQL, Redis). `docker compose -f docker-compose.yml up -d --build`, then open http://localhost:8080/apps/thematiq/ (admin / admin). Remove it with `docker compose -f docker-compose.yml down -v`.
- `thematiq-compose.yaml`: demo environment built from release tarballs, on http://localhost:8604. The file itself says it is not a development environment.

For development the app is checked out inside a Nextcloud server tree (`apps-extra/` or `custom_apps/`). The PHP unit suite needs that tree: `composer test:unit` looks for `../../lib/base.php` and skips the suite without it.

## Build

```bash
composer install     # PHP dev tools; also sets git core.hooksPath to .githooks
npm ci               # JS dev tools; the prepare script also sets core.hooksPath
npm run build        # fonts, Marianne fonts, icons and the code editor bundle
```

Generated files have a generator and a `--check` twin in `package.json`, for example `npm run generate:lasuite-tokens` / `npm run test:lasuite-tokens` and `npm run l10n:build` / `npm run check:l10n-js`. Regenerate with the generator; never hand-edit the output. After editing a token set by hand, run `bash scripts/token-set-gate.sh` (see `docs/features/token-sets.md`).

## Test

```bash
npm run test:unit        # Vitest (tests/vitest)
npm run test:coverage    # Vitest with v8 coverage
composer test:unit       # PHPUnit (tests/Unit); needs a Nextcloud server tree, skips otherwise
npm run test:l10n        # every used translation key is in l10n/en.json and every locale
```

End-to-end tests are Playwright (`playwright.config.ts`, specs in `tests/e2e/`). There is no npm script; run it against your own disposable instance:

```bash
PLAYWRIGHT_BASE_URL=http://localhost:8095 npx playwright test
```

The suite refuses the shared instance on http://localhost:8080 unless you set `THEMATIQ_E2E_ALLOW_SHARED_INSTANCE` to that origin (`tests/e2e/base-url.ts`, `tests/e2e/shared-instance.ts`). It runs with one worker; do not raise `--workers`.

## Lint and quality

```bash
composer check:strict    # lint, phpcs, cs:check, phpmd, psalm, phpstan, test:all
composer check           # lint, phpcs, psalm, test:unit
composer cs:fix          # php-cs-fixer
composer phpcs:fix       # phpcbf
npm run lint             # ESLint
npm run stylelint        # Stylelint on css/
npm run format           # Prettier check
npm run check:manifest   # validate src/manifest.json against the app manifest schema
```

The composer checks print `ALL CHECKS PASSED - EXCEPT test:all, WHICH DID NOT RUN` outside a Nextcloud server tree. That line says nothing about the PHP tests.

## OpenSpec flow

`openspec/config.yaml` uses the `spec-driven` schema.

1. A change starts in `openspec/changes/<name>/` with `proposal.md`, `design.md`, `tasks.md`, often `screens.md`, and delta specs in `specs/<capability>/spec.md`.
2. When it ships, its specs are merged into `openspec/specs/<capability>/spec.md`.
3. The change folder moves to `openspec/changes/archive/<YYYY-MM-DD>-<name>/`.

`openspec/parity/` and `openspec/features.overlay.json` hold capability and feature metadata. The committed pre-commit hook regenerates `docs/features.json` when `openspec/specs/` or the overlay change.

## Architecture decisions

Decisions are recorded per change in the "Decisions" sections of `openspec/changes/archive/*/design.md` (and `design.md` in open changes under `openspec/changes/`). The `css/` layer order and configuration keys are summarised in `project.md`; the newer design files take precedence where they differ.

## Conventions

- The app id is `thematiq`; the NL Design System names (`--nldesign-*` CSS properties, `nldesign` class prefixes, the `nldesign` design-system id) belong to the external standard and must not be renamed. The comment in `appinfo/info.xml` explains why.
- Token sets are data: a shipped set is `css/tokens/<id>.css` plus an entry in `token-sets.json`, with no PHP change (`docs/features/token-sets.md`).
- Design systems are stylesheet bundles declared in `design-systems.json` and read by `lib/Service/DesignSystemService.php`; their CSS lives in `css/systems/<id>/`.
- `src/manifest.json` is observability-only (health checks). The app renders no manifest-driven pages.
- Translations: `l10n/<locale>.json` is the source; `l10n/<locale>.js` is generated by `npm run l10n:build`.

## Commits

Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, `refactor:`), present tense, imperative mood, as `CONTRIBUTING.md` describes. No commit-message lint is configured in this repository. Branch from `development` and open the pull request against `development`.
